# Agent Execution Realms

Status: Implemented

## Summary

Agent execution realms let workflows run LLM agents inside isolated environments, such as long-lived Docker runner containers or Azure Container Apps dynamic sessions. Workflows select these environments using the standard `execution.profile` configuration.

Previous Conductor releases supported Docker execution profiles for script steps only. Agent execution realms extend that placement model to agent steps. The agent loop, its stdio MCP child processes, staged skills, and plugins run colocated inside the target execution environment instead of running directly inside the host process.

## The `run_agent` Seam Contract

Conductor isolates backend execution behind the `RunnerBackend` interface in `conductor.execution.backend`. The `run_agent` method provides the seam for agent execution:

```python
async def run_agent(
    self,
    spec: AgentSpec,
    lease: WorkspaceLease | None,
    *,
    on_event: AgentEventSink | None = None,
    interrupt_signal: asyncio.Event | None = None,
    execute_local: Callable[[], Awaitable[AgentResult]] | None = None,
) -> AgentResult:
```

The seam contract relies on two frozen dataclasses defined in `conductor.execution.types`:

1. `AgentSpec`: A transport-neutral description of a single agent call. It carries the model provider identity, rendered prompt, system prompt, output schema, tool configuration, MCP servers, context dictionary, staged skill paths, custom agent definitions, per-call environment overlay, provider credentials, and execution settings. Credential fields set `repr=False` to avoid leaking secrets in debugging output.
2. `AgentResult`: The outcome of the invocation, capturing output content, token usage, session duration, and partial completion flags. Local in-process runs can also carry opaque references to continuation state and raw provider responses, but those fields never cross remote transports.

### Transport Neutrality Rule

The `AgentSpec` contract stays strictly neutral across execution backends. It contains no Docker flags, no HTTP URLs, and no cloud provider identifiers. Evolution follows three rules:

* **Additive evolution**: New capabilities add optional fields with safe defaults. Existing callers continue to work without modification.
* **Adapter payloads**: Each backend adapter serializes `AgentSpec` into its own wire transport format. For example, Docker and ACA runners consume JSON payloads generated by `conductor.execution.agent_wire`.
* **Capability declarations**: Backends declare which capabilities they honor through `RunnerCapabilities`. Callers inspect flags such as `capabilities.agent` and `capabilities.interrupt` rather than querying backend class names.

## Runner Image Recipe

A runner is simply any container image with Conductor installed. Because Conductor packages its runner server in the standard distribution, installing Conductor equips the image to act as an execution runner.

The canonical reference implementation lives in `docker/aca-runner/Dockerfile`. Building a custom runner image typically starts from that base or copies its pattern:

```dockerfile
FROM python:3.12-slim

# Install system dependencies and runtimes needed by MCP servers
RUN apt-get update && apt-get install -y --no-install-recommends \
    git ca-certificates curl nodejs npm \
    && rm -rf /var/lib/apt/lists/*

# Install pre-baked MCP server packages
RUN npm install -g --no-fund --no-audit @cyanheads/git-mcp-server@2.15.1

# Install Conductor (which includes conductor.aca_runner)
ARG CONDUCTOR_VERSION
RUN pip install --no-cache-dir \
    "conductor-cli @ git+https://github.com/microsoft/conductor.git@${CONDUCTOR_VERSION}"

# Configure default workspace and unprivileged user
RUN useradd --create-home --shell /usr/sbin/nologin runner \
    && mkdir -p /workspace \
    && chown runner:runner /workspace
WORKDIR /workspace
USER runner

# Run the in-container runner server
CMD ["python", "-m", "conductor.aca_runner"]
```

### Baked-in Stdio Binaries Contract

The runner image contract requires tools declared by stdio MCP servers to be pre-installed inside the container image. During request preflight, the runner server inspects `mcp_servers` with `_check_stdio_binaries`.

If a declared stdio binary (such as `git-mcp-server` or `npx`) is missing from the container PATH, the runner rejects the call immediately with an actionable error. It prompts the operator to install the binary into the image or remove the server from workflow configuration.

### Protocol Version 2 Handshake

When starting an agent realm, Conductor queries the runner `GET /health` endpoint to verify readiness. The runner returns its protocol version and supported features:

```json
{
  "ready": true,
  "conductor_version": "0.2.0",
  "protocol_version": 2,
  "features": ["interrupt"]
}
```

Docker agent realms require `protocol_version == 2` and reject an older image before sending agent requests, with an error asking the operator to rebuild it. ACA execution profiles can negotiate version 1 with an older image, but cannot deliver agent-scoped secrets there; the legacy `provider: aca` form also retains its version 1 wire format unless targeted interrupt is available.

## Docker Realm Transport

Docker agent realms use a lease-lived runner container created on top of the workflow shared workspace volume. Rather than exposing a network port on the host, Conductor communicates with the runner over an internal bridge.

### Container Bridge Over `docker exec -i`

The host process runs `docker exec -i <container> python -m conductor.runner.bridge` to talk to the runner. The bridge runs inside the container network namespace and forwards standard input to the runner loopback address at `http://127.0.0.1:8080`.

Stdout streams NDJSON event frames directly back to Conductor. This design delivers several benefits:

* **No published ports**: Docker does not publish the runner port. With an isolated container network it stays on container loopback; with `docker.network: host`, loopback is shared with the host, so other host processes can reach the runner and concurrent runners may contend for the port.
* **Remote daemon compatibility**: The bridge relies entirely on standard Docker client execution pipes. It works unchanged across local Docker daemons, rootless Docker, and remote `DOCKER_HOST` setups.
* **Shielded lifecycle**: Host-side streaming reader tasks track progress incrementally while shielding container cleanup operations from premature cancellation.

## Interrupt Semantics and Degradation

The runner exposes `POST /interrupt` to pause in-flight agent loops gracefully.

### Targeting and Status Codes

Each invocation assigns a unique `execution_id` in `AgentSpec`. When an operator cancels or interrupts a run, the host issues an interrupt request with that ID.

The runner evaluates the request against its internal execution registry:

* **200 OK**: The execution was active and accepted the interrupt signal. The inner provider halts iteration and frames partial results.
* **404 Not Found**: The execution ID is not active and not recorded.
* **409 Conflict**: The execution has already completed or previously received an interrupt signal.
* **422 Unprocessable Entity**: The request body omitted the required `execution_id`.

For Docker realms, the host stops issuing new interrupts once it receives a
terminal result. An interrupt already in flight can race completion and return
409; the host drains the execute stream and preserves its full or partial result.
After either an accepted interrupt or a conflict, one 30-second deadline covers
the remaining stream, bridge-process exit, and stderr drain. Delivery failures or
an expired deadline fail the invocation and retire its runner. An accepted
interrupt must produce a partial result; a conflict does not require one.

### Graceful Degradation on Older Images

If a runner image does not advertise the `interrupt` feature in its `GET /health` handshake, Conductor handles interrupts by racing the stream reader against the interrupt event. When triggered, the host logs a single warning, ceases reading frames, and marks the turn as partial.

### Legacy ACA Behavior Note

Workflows using the legacy `provider: aca` syntax benefit from this mechanism when running against rebuilt runner images. In earlier versions, interrupting an ACA session relied on best-effort HTTP session deletion that cloud custom containers often refused. With a protocol v2 image, the legacy facade sends targeted interrupt signals directly, restoring graceful pauses without session teardown.

## Environment Overlay and Reserved Names

Agent-scope secrets reach remote realms through a dedicated per-call `env_overlay` channel. This channel separates secret delivery from model credentials and control process environments.

### Delivery Target

The `env_overlay` applies strictly to the spawn environment of stdio MCP child processes inside the runner container. It does not modify `os.environ` in the runner process itself, nor does it reach the model provider SDK.

### Reserved Environment Names

To prevent collisions with model provider authentication variables, Conductor statically reserves sensitive environment names. The compiler and validator reject any agent-scope secret whose `delivery.env` matches one of the following names (evaluated case-insensitively):

* `base_url`
* `api_key`
* `bearer_token`
* `github_token`
* `GITHUB_TOKEN`
* `GH_TOKEN`
* `COPILOT_GITHUB_TOKEN`
* `COPILOT_PROVIDER_API_KEY`
* `COPILOT_PROVIDER_BEARER_TOKEN`
* `OPENAI_API_KEY`
* `ANTHROPIC_API_KEY`

If a workflow attempts to map an agent-scope secret to a reserved name, Conductor halts at validation time and prompts the author to choose an MCP-specific variable name.

## Provider Support Matrix

Remote execution realms decouple the execution environment from the model provider. However, the in-container runner must know how to instantiate the model provider client.

The following table summarizes provider support across execution environments:

| Model Provider | Local Realm | Docker Agent Realm | ACA Agent Realm |
|---|---|---|---|
| `copilot` | Supported | Supported | Supported |
| `openai` | Supported | Supported | Supported |
| `claude` | Supported | Supported | Supported |
| `claude-agent-sdk` | Supported | Not supported | Not supported |
| `hermes` | Supported | Not supported | Not supported |

Selecting `claude-agent-sdk` or `hermes` on a remote profile triggers a static configuration error during manifest compilation and validation. The error identifies supported providers and notes that other engines require follow-up implementations.

Remote profiles also reject `dialog:` until evaluation and conversation turns have a
runner contract. Remote Copilot rejects `runtime.max_tokens`, which its runner SDK
cannot enforce; OpenAI and Claude receive their configured generation limits in the realm.

## Skills and Plugins Staging

Agents frequently rely on local skills or repository plugins. How these dependencies reach the agent depends on the realm backend.

### Docker Realm Staging

Docker realms mount the run-scoped bundle volume at `/workspace`. Before invoking the agent, Conductor maps host file paths to container paths using the content-addressed bundle manifest:

* Declared skill directories map to `/workspace/skills/<name>`.
* Plugin directories map to `/workspace/plugins/<name>`.
* Relative working directories resolve against `/workspace/main/` for the main workflow root, or against `/workspace/roots/<NN>/` when files originate from additional bundle roots.

If a workflow refers to a skill or plugin directory that was omitted from the bundle topology, Conductor raises a `ConfigurationError`. The message advises adding the directory to `workflow.bundle.additional_roots`.

### ACA Realm Carve-out

Azure Container Apps sandboxes operate without a staged workspace volume mount. Consequently, skills and plugins are not supported on ACA execution profiles.

Declaring skills or plugins on an agent assigned to an ACA profile fails static validation. Authors needing custom skills in ACA must bake them directly into their runner container image or use Docker execution profiles.

## Resume Semantics and Image Updates

Conductor treats remote agent steps under an at-least-once rerun model during `conductor resume`.

Because remote container state is ephemeral across runs, resuming a workflow reruns the agent from its initial inputs rather than restoring mid-turn Python frames.

Consistent with Docker script profiles, Conductor records the runner image name in the run manifest but does not pin the resolved image digest against resumption. If an operator edits `runner_image` in the environment document before resuming, the updated image takes effect immediately upon restart.

## Security and Trust Boundaries

Docker agent realms can isolate agent and tool processes from the Conductor host when the operator chooses an isolated container network. These boundaries do not make credentialed agent workloads safe to treat as untrusted:

* **Loopback isolation**: A Docker runner listening on `127.0.0.1` is private to its container only with an isolated network namespace. With `docker.network: host`, that address is host loopback, so other host processes can reach it. The ACA runner is bound for its session gateway instead; its reachability and isolation depend on the ACA pool configuration.
* **No ambient host inheritance**: Remote profiles default `inherit_control_environment` to false. The control process environment is not passed wholesale to the runner.
* **Per-call secret injection**: Secrets travel through the `env_overlay` parameter in the POST payload. They never appear in container creation arguments, inspect metadata, or filesystem configs.
* **Operating system process boundary**: Environment variables passed to stdio MCP children reside in those child processes. Anyone with root access or permission to inspect `/proc/<pid>/environ` inside the container can inspect those variables. Conductor guarantees protection on the host and runner communication boundary, not kernel-level isolation inside the container itself.

## Operator Sizing and Concurrency

Conductor reserves one runner container per concurrently active agent invocation. An idle runner may be reused for a later sequential call; if an invocation is cancelled, only its owned container is retired, so another active invocation can continue. All runners for a lease share its staged workspace volume.

Conductor does not artificially throttle parallel agent invocations. The platform operator is responsible for sizing daemon resources, CPU limits, memory allocations, and ACA session pools for the expected peak number of concurrent runners.
